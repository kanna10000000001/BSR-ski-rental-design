# 数据库结构与迁移说明

## 为什么改

原来的 `bsr_state/main` 同时放门店、装备、预约、合同和维修等数组。每处理一次业务，云函数都要读写整份文档。课堂数据很少时可以运行，但记录增加后，文档大小和写入范围都会跟着变大。

## 现在怎样保存

实际使用的是腾讯云 CloudBase 文档数据库。仍在原来的 `bsr_state` 集合中，`main` 保存 `schemaVersion=2`、业务版本、流水编号和最近的请求编号。以下分组文档的 `items` 数组保存各类记录：
| 文档 ID | 保存内容 | 主要关联 |
| --- | --- | --- |
| `data_stores` | 东、西门店 | `storeId`、`location`、`home` |
| `data_employees` | 门店员工 | `employeeId` |
| `data_contractors` | 维修承包商及费率 | `contractorId` |
| `data_equipment` | 装备、当前状态和位置 | `equipmentId` |
| `data_customers` | 客户档案 | `customerId` |
| `data_reservations` | 顾客预约与受理状态 | 预约编号、微信身份 ID |
| `data_contracts` | 合同及其租赁段 | 合同编号、客户编号、装备编号 |
| `data_repairs` | 报修、工时及验收 | 维修单号、装备编号、承包商编号 |
| `data_shifts` | 排班 | 员工编号、门店编号 |
| `data_audit` | 操作记录 | 操作人、目标编号 |

`bsr_users`、`bsr_web_users` 和 `bsr_web_sessions` 继续分别保存微信员工授权、网页登录账号和会话。客户端不能直接读写上述集合，业务规则仍由云函数执行。

合同中的租赁段保留借出时的单价、门店和时间；维修单保留当时采用的工时费率。以后调整装备价格或承包商费率，不会倒改历史记录。编号仍沿用原来的规则，不重新编号。
